## 💡 Идея 37: KV-Cache для Инкрементального Сканирования

**Исток:** `KATCharLM.hs` (строки 226-338) — `KVCache`, `forwardLayerCached`, `prefill + decode`.
При генерации текста каждый новый токен проходит через **все** накопленные K/V в кэше, а не пересчитывается заново. Сложность: O(T) за новый токен вместо O(T²).

**Интеграция в Duo Agents:**
- При инкрементальном сканировании PR (delta scan), мы **не пересчитываем KAN** для всех файлов проекта.
- Только изменённые файлы проходят через KAN, а для остальных мы используем кэш "ключ-значение" (`K_cached`, `V_cached`) из предыдущего скана.
- `Prefill`: При первом сканировании строим полный KV-кэш всех файлов.
- `Decode`: При каждом новом коммите/PR обновляем только кэш затронутых файлов.
- **Ожидаемый результат:** 10-100x ускорение повторных сканирований при CI/CD. Инвалидация кэша — по графу зависимостей (Idea 27: Graph KAN Routing).

## 💡 Идея 38: Reverse-Mode AD для Backprop через Security Scorer

**Исток:** `ReverseAD.hs` (95 строк) — аналитический backward для цепочки `LoRA → LMHead → CrossEntropy` с O(T×d×r) вместо O(N×T²). Явный chain rule: `dL/dA = x^T × dL/dtmp1`, `dL/dB = tmp1^T × dL/dtmp2`.

**Интеграция в Duo Agents:**
- Наш текущий ForwardAD (Фаза 28) использует `∂CVSS/∂threshold` через дуальные числа — это O(N) проходов для N параметров.
- С **Reverse-mode AD** мы получаем ВСЕ N градиентов за ОДИН backward pass.
- Конкретно: цепочка `ScanInput → KAN → LoRA → CVSS_Score → Loss`. Аналитический backward:
  - `dL/dCVSS = 1` (мы хотим минимизировать/максимизировать)
  - `dL/dLoRA_A = x^T × (dL/dLoRA_out × B^T)` — прямо из `ReverseAD.hs`!
  - `dL/dLoRA_B = tmp1^T × dL/dtmp2`
- **Ожидаемый результат:** Авто-тюнинг ALL параметров секьюрити-скорера за один проход. Масштабируется до 1000+ параметров.

## 💡 Идея 39: Differentiable Policy (KAN as RL Routing Agent)

**Исток:** `LogisticsKAN.hs` (251 строк) — `kanPolicyLoss`: KAN как policy network для маршрутизации транспорта. State vector → KAN → softmax → argmax station. Тренировка через AD: минимизация `total_wait` дифференциируемой симуляции.

**Интеграция в Duo Agents:**
- Вместо жёстких правил "какой файл сканировать следующим", используем **KAN как RL-политику**:
  - `State = [queue_sizes, thread_utilization, surge_multipliers, gravity_scores]`
  - `Action = KAN(State) → softmax → select_file_for_scan`
  - `Reward = -total_scan_time - missed_vulnerabilities`
- KAN тренируется через **дифференциируемую симуляцию** (как в LogisticsKAN): мы симулируем N сканирований и берём градиент total_cost по параметрам KAN через AD.
- **Ожидаемый результат:** Сканер, который САМИ УЧИТСЯ оптимальному порядку проверки файлов. Не нужны ручные правила приоритизации — KAN обучается минимизировать время до обнаружения уязвимости.

## 💡 Идея 40: Frozen/Trainable Split (Полиморфный AD для Секьюрити-правил)

**Исток:** `FineTune.hs` (216 строк) — `forwardFTLayerAD`: KAN заморожен (`constD`), LoRA обучаема (`Dual`). Полиморфный forward проход: один код, два режима через generics `(Floating a, Ord a) =>`.

**Интеграция в Duo Agents:**
- Разделить секьюрити-движок на **Frozen Core** и **Trainable Adapters**:
  - `Frozen`: Базовые правила OWASP/CWE — не меняются, прошли аудит, сертифицированы.
  - `Trainable (LoRA)`: Тонкая настройка под конкретный проект — обучается на исторических CVE данного проекта.
- Используя полиморфный AD: один и тот же forward проход компилируется в два режима:
  - `evaluate(constD)` — быстрая оценка без градиентов (production scan)
  - `evaluate(Dual)` — медленная с градиентами (training/tuning mode)
- **Ожидаемый результат:** Гарантированная стабильность core-правил (они физически не могут измениться при тюнинге) + адаптивность под проект через LoRA. Как в LLM: GPT замораживается, LoRA дообучается.

## 💡 Идея 41: Top-K Security Sampling (Стохастический Аудит)

**Исток:** `Generation.hs` (94 строки) — `sampleTopK`: вместо greedy argmax, выбираем из top-K кандидатов с температурой. `CharLM.hs` — Top-K + temperature для текстогенерации.

**Интеграция в Duo Agents:**
- При сканировании больших проектов (10K+ файлов) полный аудит невозможен. Вместо сканирования ТОП-1 файла по приоритету, используем **стохастический Top-K sampling**:
  - `Temperature=0.1` → Почти детерминированное сканирование (всегда ТОП файлы). Для CI/CD.
  - `Temperature=0.8` → Случайное исследование (находим "неожиданные" уязвимости). Для ночных аудитов.
  - `Temperature=1.5` → "Хаотический" режим (красная команда, fuzzing). Для penetration testing.
- Каждый скан-раунд: берём Top-K файлов по KAN приоритету, нормализуем вероятности, сэмплируем с температурой.
- **Ожидаемый результат:** Exploration vs Exploitation trade-off для секьюрити-аудита. Высокая температура находит уязвимости в неочевидных местах. Низкая → быстрый CI/CD. Как в MCTS (Monte Carlo Tree Search), но для Code Security.
